Overview

Real-time insurance verification for healthcare providers

Introducing the Electronic Patient Insurance Checker — a web application that streamlines the treatment process with real-time insurance verification. Background

Slow enrollment, complex eligibility, gaps in patient care

Major health insurance providers are designated to offer coverage for specific drugs to recipients. However, a significant hurdle lies in the intricate eligibility determination process, leading to a slow enrollment rate.

As a prominent consulting firm in the healthcare sector, the objective was to develop a web application for Healthcare Providers (HCPs) to facilitate eligibility checks — enabling HCPs and care providers to effortlessly access this information, ensuring patients receive the care they deserve and bridging existing gaps.

Problem Statement

A process so complex it increases rejection rates

Create a web application that is interactive, streamlining the eligibility determination process for a specific drug and guaranteeing high acceptance rates.

UX Strategy

Simplify, guide, and personalise at every step

The design process focused on enhancing the usability, accessibility, and simplification of the application filling process for Healthcare Providers (HCPs) to achieve the desired results. The designs aimed to streamline the process, making it intuitive, engaging, and ensuring a seamless experience for users.

Design Decisions

Six principles that shaped the experience

Application flow

Confirmations

Each completed section surfaces a summary before the user moves on. The application never advances silently — the HCP always sees what was captured and can correct it before proceeding.

Question prompts

Human-like guidance

Contextual prompts appear when a question is left unanswered or an answer is inconsistent. Rather than showing a generic error, the system explains what it needs and why — the way a knowledgeable colleague would.

Benefit report

Visible trust markers

Coverage prediction and prior authorisation status are shown proactively — not hidden behind a final submit. HCPs can see the likely outcome before they finish, making the decision to continue or correct feel informed, not a leap of faith.

Sections · Delegation

Assisted flows

The application is broken into bite-size sections so the HCP is never confronted with the full document at once. A delegation option lets a second person take over mid-application — no progress is lost, no duplication required.

Navigation · Save

Easy reversibility

Users can return to any previous section without losing what they entered. Mandatory fields are flagged inline as you go — not in a batch error at the end — so corrections are small and local, not a full restart.

Microcopy

Language that reduces fear

Insurance and eligibility terminology is replaced with plain-language equivalents throughout. Error messages say what is needed, not what went wrong. Every label, prompt, and status is written to inform — not to intimidate.

This project involved designing an end-to-end healthcare web application that simplified a complex insurance eligibility process for both Healthcare Providers and patients — reducing friction, improving acceptance rates, and enabling guided, personalised workflows.

Design Language

Before any token was created, Thematic began with a Taste Profile — a written brief setting the emotional target for every decision that followed. The brief: a trusted senior colleague. Precise, warm, never loud.

Five design principles

Hierarchy over decoration

Every visual element needs a purpose. Typography, spacing, and alignment do the structural work — no decorative dividers, gradients, or embellishments.

Density earns trust

Enterprise users work with information all day. Interfaces present meaningful data without excessive scrolling, while staying readable.

Blue anchors, neutrals carry

A single primary blue (#1518A6) reserved for interactive and active states only. The constraint forces hierarchy to emerge from scale, weight, and structure — not colour.

States are never ambiguous

Hover, focus, active, disabled, loading, error, and success each have distinct visual language. Users should never guess whether something is interactive.

Warmth comes from restraint

Slightly off-white surfaces, warm neutrals, moderate border radii. The system feels human because it avoids coldness — not because it adds decoration.

Token Architecture

Design decisions flow through three tiers — Base → Alias → Component. Product code never references base tokens directly. All implementation flows through semantic and component layers. Token names follow a consistent format: --component-{name}-{tier}-{property}-{state} — readable by humans and AI without lookup.

Design Tokens

A deep-dive into what design tokens are, why they matter, and how to structure, name, and deploy them effectively across a scalable design system.

RoleSenior UI/UX Designer
CompanyIndegene
TypeThought Leadership · Article

What is a design token?

Design tokens are named entities that store visual design attributes — an agnostic, human-readable abstraction of visual styles that sync with all style files in the system. They allow teams to create a scalable and consistent visual system for UI development, replacing hard-coded values like hex codes and pixel values with meaningful names.

Why use a design token?

Design tokens are versatile

Because tokens are platform-agnostic, they are independent of any specific tech stack. A single source of truth can be implemented across web, iOS, Android, and other platforms simultaneously.

Three-tier token structure

Tokens are organized into three layers, each with increasing specificity and isolation — base tokens, alias tokens, and component tokens. Each layer references the one below it, creating a clean hierarchy that makes global changes predictable and targeted changes precise.

Difference between styles and design tokens

Types of values that can be stored

Token Strategy

By simply observing a token name, both designers and developers should intuitively understand its purpose — without needing documentation. The strategy involves grouping components categorically, assigning each to a specific category to inform the token naming convention.

Benefits of this approach:
  • Consolidating repetitive tokens into a single category significantly decreases total token count
  • Better manageability and clear visual hierarchies, reducing cognitive load
  • Reducing token inventory by up to fifty percent
  • Enhanced control over design operations with standardized tokens

Token Taxonomy

Efficiently deploying design tokens is crucial — without a clear taxonomy, token generation quickly becomes unwieldy and leads to an unmanageable inventory. A well-structured taxonomy makes naming conventions intuitive and consistent across the entire design system.

Base and alias tokens

Each alias token is designated with a distinct purpose, meaning, and function. Unlike base tokens, alias tokens are exclusively used within predefined contexts or instances. Naming conventions for alias tokens should balance abstraction with clarity — accommodating various values while conveying their intended use.

Token updates and isolation

The hierarchical structure of design tokens facilitates the concept of isolation and control within a design system. Each tier has a different scope of impact when updated.

Base tokens — zero isolation, changes affect the entire system

Alias tokens — moderate isolation, changes affect defined contexts

Component tokens — highest isolation, changes affect only that component

Token pipeline and workflow

The process utilises the open-source Figma Token Studio plugin to generate tokens and export them to GitHub in JSON format. The tokens are then analyzed through Style Dictionary on GitHub and converted to CSS variables for use in code — creating an end-to-end automated token pipeline.

The foundation

The foundation is pivotal in a design system and requires meticulous planning to ensure it is fail-safe, as components derive their styles from the system's atomic elements to provide functional and beautiful product experiences.

"A design system is a perpetually evolving entity. Putting a final touch on it and declaring it finished proves to be a challenging endeavour."

Colors

The colour atoms are carefully chosen and defined within the system so that they interact harmoniously across components to create a cohesive aesthetic. The palette is divided into four major categories — Grays (neutrals), Primary, Accent (Red, Green), and System colors — following a triadic colour scheme. Colors are accessibility-checked and pre-defined for backgrounds, interaction states, and text elements, directly informing the design token definitions.

Elevations, Spacers & Icons

Elevations and spacers serve as composite tokens within the design system, encapsulating values that define the appearance of visual elements. Elevations determine depth and shadow, contributing to hierarchy. Spacers establish consistent spacing, ensuring a balanced layout. Icons are categorised into thin and filled variants — each serving distinct purposes — with standardised sizes to align seamlessly with all interface elements.

Typography

Typography in the design system involves the systematic and intentional selection of fonts and text styles to create a cohesive user interface. Its design tokens are composite in nature, encompassing font families, sizes, line spacing, and weights — all defined to ensure consistency and readability across all components and screens.

Overview

A living design system for consistent digital experiences

In the dynamic world of design, where digital landscapes evolve at a breathtaking pace, ensuring a cohesive and harmonious user experience is paramount. Thematic.Design is a comprehensive framework meticulously crafted to foster consistency, streamline workflows, and elevate the overall aesthetic and functional quality of digital products.

At its core, the design system is more than just a collection of guidelines — it's a living, breathing organism that empowers design teams to create compelling user-centric experiences. It encapsulates brand ethos, design principles, and a shared language that resonates across every pixel and interaction.

Methodology

Atomic Design Principle

Atomic Design is a methodology created by Brad Frost seeking to provide direction on building interface design systems more deliberately and with explicit order and hierarchy. Structured from atoms → molecules → organisms → templates → pages, every decision at the foundational level cascades consistently upward — ensuring the smallest design choices scale into coherent, complex interfaces.

Foundation

Atoms — the building blocks

The atoms of a design system represent the foundational elements that serve as the building blocks for creating more complex components and structures. These atoms are the smallest units in the design system, including basic elements like typography, colours, elevations, spacing, and icons — each meticulously defined to ensure every component that builds upon them is consistent and fail-safe.

Components

Documented and prototyped for the best experience

Thematic.Design is a front-facing Figma file where all atoms and components are fully documented and prototyped. Each component page covers usage guidelines, variants, states, and interactive prototypes — giving designers and developers a single source of truth with zero ambiguity.

Overview

The Attendance Management System is a web-based platform built for facility management teams overseeing large, multi-department workforces. Attendance, leave, and roster planning had no shared home — managers were working across spreadsheets, paper registers, and disconnected tools, with no way to detect when records conflicted. Designed, built, and deployed end to end.

A backlog badge flags unresolved items from past days before they reach month-end. Below that, an org breakdown table shows department-level attendance counts at a glance. The screen is read-only by design: it tells you what needs doing, then gets out of the way.

Attendance

The attendance screen organises staff by department in a left-side rail. Each employee shows their live status — Present, Absent, Late, On Leave, Half-day — alongside kiosk check-in and check-out times. Clicking an employee opens an edit drawer with their last seven days of history, a Mark As dropdown, and fields to override times manually. When a leave approval conflicts with an attendance record, the system flags it automatically.

Edit attendance — user flow

Backlog

A dedicated tab for gap days and conflicting records that couldn't be resolved at the time of marking. Supervisors work through backlog items before month-end so nothing reaches payroll unchecked.

Backlog resolution — user flow
Leaves

The Leave and Time Off screen is where managers and supervisors handle all leave requests across the team. Sick Leave and Casual Leave can be applied, approved, rejected, or reversed from a single interface, with a calendar view to check coverage before confirming. An approved leave automatically updates the corresponding attendance record — no manual reconciliation.

Leave approval — user flow
Foundation screens

Before any attendance can be tracked, the system needs to know the structure of the organisation. Foundation covers Departments and Roles, Shifts, Branches, Vendors, and Employees — the configuration that everything else depends on. These screens are set up once and rarely revisited, but they are the source of truth for every downstream function. Adding an employee is a three-step flow: identity, assignment, and review. Role options filter by department, shift options filter by branch, and nothing can be saved without the required fields in place.

Roster

The roster is a grid of employees against days — the most complex screen in the system. Managers assign weekly off days, track shift patterns, and catch leave conflicts before the month begins. The grid supports two views: a compact month view and an expanded week view. Bulk weekly-off selection uses a floating action bar so managers can update multiple employees in one action. A key rule throughout is WO-priority: if an employee's approved leave falls on their weekly off day, it counts as WO and not against their leave balance. Save-with-undo means changes go through immediately, with a brief window to reverse.

Five design principles

Not feature decisions — the lens through which every interaction, prompt, and flow was evaluated.

Confirmations

Users should always know what will happen before it happens. Consequential actions are preceded by a moment that surfaces the outcome and asks for intent. Confirmation is not friction — it is the system making sure the person acted deliberately.

Human-like guidance

Instructions, prompts, and labels should read the way a knowledgeable colleague would speak them — plain, direct, second-person guidance that names what to do and why it matters.

Visible trust markers

A system earns trust by being honest about its own state — surfacing problems rather than hiding them, and confirming when an action has taken effect. Trust is built by making reliability legible.

Assisted flows

Complex tasks should be structured so the system carries the sequence, not the user. When a task has a required order, enforce it. The user's job is to make decisions; the system's job is to deliver them in the right order.

Easy reversibility

Errors are inevitable in high-frequency operational systems. Where an action can be undone, provide the path. Where it cannot, name the constraint clearly before the action — not after. Reversibility is a prerequisite for confident use.

Context

SafePassenger is a multi-tenant SaaS used by intercity bus operators in India. A device on each bus counts passengers boarding and alighting; the system reconciles those counts against ticket bookings to flag unscheduled boarding — passengers who board without a ticket, which is how revenue leaks (drivers pocketing cash fares).

The existing dashboard worked, but users described it as "unstructured, generic, and not operator-centric." The brief: run a proper discovery and redesign the people-counting experience.

Discovery

Research insights

Discovery ran in four structured phases: business stakeholders → users → contextual inquiry → workflow mapping (journey map). The goal was to understand the business, the users, and how the work actually happens today — before touching any design decisions.

Primary research — stakeholder interviews

Interviews with business stakeholders and the product team established the business framing and surfaced the first critical finding about who actually uses the dashboard.

Business goal

Reduce revenue leakage from unscheduled boarding and replace random, manual inspector checks with continuous automated monitoring. Success was defined loosely — a baseline of ~2 minutes of monitoring time per bus — with two non-negotiables: unscheduled-boarding alerts and hardware-tampering alerts.

The pivotal user finding

The daily user is not the paying bus operator. It's a Product Owner Operator (POO) — someone on the service provider's side who runs the dashboard across multiple fleets, validates the analysis (it isn't 100% accurate), and pushes findings to operators. The bus operator is a light consumer who acts on what they receive.

Framing decision

SafePassenger is a visibility / fare-reconciliation tool, not enforcement — it surfaces leakage; it doesn't stop theft. This single line kept scope honest for the rest of the project.

Primary research — contextual inquiry

A field study with the POO — observing them live in their working environment alongside real product screenshots — surfaced how the job is actually done. Four findings shaped every design decision that followed.

Behaviour management, not monitoring

The dashboard is only the trigger; the actual action happens in WhatsApp, where the POO manually retypes each finding to the operator ("bus 3679 · 5 unscheduled boarding in Salem · 3:19am").

The map is home

Users open the map first, scan for red/orange icons, verify via tooltip counts and boarding video — they don't live in tables.

Everything is manual

Fetching data, decoding an 8-colour legend, cross-checking tabs, and retyping into WhatsApp — the POO was the integration layer.

Workshop insight — Mental model, 5 actors

Before any structural decisions, I mapped how each actor thinks about the system — so the IA would follow users' own concepts, not the database schema. Two distinctions shaped everything: Trip Summary is separate from the detailed Trip view, and the POO spans many fleets while the Bus Operator sees only his own.

Key insight

The POO is a human integration layer — fetching, decoding a cluttered map, verifying, transcribing, and delivering by hand. Every one of those steps is a candidate to shift from person to system, with data trust as the essential precondition.

Define

Problem statement, user needs & requirements

Problem statement

"Bus operators lose revenue when passengers board without tickets, but they can't oversee trips and have no reliable visibility into where and when it happens. Today a POO manually hunts each completed trip on a cluttered map, verifies events through several steps, and re-types findings into WhatsApp — slow, effort-heavy work built on counts the team doesn't fully trust."

User needs — jobs to be done
Bus Operator

"When my buses run routes I can't watch, I want to reliably know where and when un-ticketed passengers boarded, so I can hold drivers accountable and recover lost fares."

POO

"When a trip completes, I want to quickly find and confirm real leakage events, so I can report them without manual effort or doubt."

Ideate

Map-first. Verify & draft. Human in the loop.

Rather than replace the map with a queue, I kept the map central — it's where operators already work — and made it legible. The core concept: "Verify & draft." The POO confirms each event by watching its video, then a single Final Verify generates a copy-ready message they paste into WhatsApp. Human-in-the-loop by design — the device analyses; the dashboard displays; verification stays manual.

How Might We — 4 questions that framed the work

HMW make the counts trustworthy enough that the operator acts without second-guessing?

HMW surface real leakage events without scanning a cluttered map?

HMW separate signal (real leakage) from noise (false alerts, legitimate stops)?

HMW turn a verified event into a shareable, actionable message — without manual transcription?

Design decisions — insight to decision

No counting logic in the UI

The device analyses; the dashboard should only display. Impossible values shown as a neutral "under review" state — not "−10".

Tampering → video, not a label

Show "Tampering detected" and route the POO to video — never a false "turned" or "covered" label. Tampering is its own event type; Device Health holds only unattributed faults.

One trip, one message

Unscheduled boarding, drop-offs, and tampering roll into a single report — not three separate messages.

"Repeat offender" → crew trust meter

A red→green gauge where the number and "flagged X of Y trips" appear only on hover. Factual, humane. Ethics is a design surface, not an afterthought.

Usability Testing

Two independent participants converged on the same six issues

I ran a moderated, think-aloud usability test on the low-fi prototype — ~11 scenario-based tasks across detect-and-report, bus device health, and trip history. Chosen deliberately over unmoderated: with a small sample and an early prototype, I needed the why behind actions, not just click data.

What held up ✓

Core verify-and-report flow worked end to end — detect → verify on video → Final Verify → copy → mark-as-sent without being blocked.

"I decide what to send" control was the emotional highlight — the human-in-the-loop model was exactly what users loved.

Alert-table-first behaviour validated — users went straight to the highest-unscheduled bus as "maximum revenue leak."

6 converging issues ✗

Operator identity is missing

"Don't show my name, show ACLS Travels — that's my focus."

Video model is wrong

Wanted chunked clips per event, with in/out direction + timestamp.

Map isn't interactive enough

Unlabeled icons; users fell back to the table every time.

Verify → message needs guidance

Both needed a hint to discover the multi-select-then-report action.

Copy-only handoff felt thin

Users pushed for deep-links to evidence, or in-app send.

Crew belongs in the report

"Put the driver's name in the message — the operator knows the driver better than I do."

Reflection

Where the real design decisions happened

Persona

Design for the real job, not the stated one

The brief was "a counting dashboard"; the job was "help me report leakage and act on crew." Correcting the persona — the POO, not the bus operator — reframed the entire product.

Research

Follow the data to where the work happens

Following findings to WhatsApp revealed the real opportunity: the dashboard's job isn't just to display, it's to produce a trustworthy, shareable output.

Trust

Trust is a feature

When the whole product hinges on believing a number, showing evidence (video) beats claiming accuracy.

Ethics

Ethics is a design surface

Swapping "repeat offender" for a crew trust meter was a small change with a big integrity payoff — the product only surfaces boarding; it doesn't prove intent.

This project shifted SafePassenger from a monitoring tool the team didn't trust into a verify-and-report workflow built around the POO — the person who actually does the work. Every structural decision, from the IA to the tab consolidation to the Final Verify flow, traces back to a single research finding: the human was the integration layer. The design's job was to replace that with a system.

Still in progress. Usability testing is ongoing — participant sessions are running and findings will feed directly into the next design iteration. High-fidelity visual design follows once testing wraps.
